# XKE.DotNet8 当前重构问题手册

> 更新时间：2026-04-24
> 范围：`Z:/XKE/XKE.DotNet8/`

## 1. 总体判断

当前 `.NET` 重构路线已经稳定，核心进度可以视为：

> DesktopHost / Auth / Notice / Desktop settings / Schedule / Network / Telemetry / Feedback / Course framework 已进入当前基线。

当前最大风险不再是“能不能跑起来”，而是：

- 避免 `WebHost` 和前端主控制器继续膨胀成新的巨石。
- 避免旧登录器思维回流，破坏“本地可信状态”主线。
- 避免传统教务验证码、Course 抢课、云上传这些后置能力提前污染当前已交付切片。
- 当前阶段前端暂不拆分，重点放在后端长期结构和兼容边界。
- 隐私落盘增强暂缓，默认用户电脑处于相对可信环境。

## 2. P0 问题

### P0-1：首登初始化必须保持原子性

首登初始化现在包含移动教务认证、资料落库、偏好落库、当前课表刷新落库。

风险：

- 如果课表失败但仍留下 session 或凭据，会让账号进入半初始化状态。
- 如果前端把首登后额外刷新作为必需路径，会造成重复联网和状态漂移。

当前措施：

- `AuthService` 在课表初始化失败、移动 token 缺失或身份信息不可用时回滚 session、凭据、移动 token 和新建学生目录。
- WebHost 测试已覆盖首登成功返回 `cached_schedule`、token 缺失回滚、课表失败回滚、本地恢复 `connected=false`。

### P0-2：已有本地凭据只能做本地校验

已有本地凭据后，`/api/auth/login` 不再承担远端刷新职责。

风险：

- 如果本地凭据校验时顺手访问移动教务，会把“本地可信进入”和“远端数据维护”混成一个动作。
- 如果本地数据不完整仍进入工作区，会造成空 dashboard、空课表或误判登录成功。

当前措施：

- 已有本地凭据时只校验 DPAPI 中保存的本地密码。
- 校验通过后必须确认本地 profile 与本地课表完整。
- 本地 profile 或 schedule 缺失时返回“本地初始化数据不完整”，不创建新 session。
- `/api/auth/session` 与 `/api/auth/trusted-login` 同样拒绝半初始化工作区。
- `/api/auth/reinitialize` 是显式修复入口，成功后刷新本地 profile、schedule、credentials；失败时保留原 trusted token 和原凭据。

后续要求：

- 不允许把首登课表刷新改成“可选成功项”。
- Notice 同步可以降级，但必须通过 warning 或公告面体现。
- 远端 connect / schedule refresh 失败不得删除 trusted account、session 或本地课表。

### P0-3：前端 trusted 状态不能退回单账号 remember-me

当前长期入口已经切到：

- `xke-trusted-accounts`
- `xke-last-account`

风险：

- 如果继续使用旧 `xke-remembered-login` 作为主状态，多个账号和可信设备语义都会失真。
- 注销如果清除 trusted accounts，会破坏“退出只结束当前 session”的语义。

当前措施：

- 旧 remembered 数据只做一次迁移，迁移后不再作为主来源。
- 前端新增 trusted account 选择器和忘记本机账号动作。

后续要求：

- 新增登录 UI 时不得重新引入 `记住我` 单开关。
- 账号清理必须是显式“忘记此设备上的账号”。

## 3. P1 问题

### P1-1：`XkeWebHostApplication` 仍需要拆分

现状：

- 多个业务路由已经集中在 `XkeWebHostApplication`。
- 虽然已有方法级拆分，但仍在同一宿主类内增长。

建议：

- 业务 endpoint 文件已存在，下一步重点不是继续按文件数量拆，而是提取服务注册、通用 session/context 加载、blocked policy 和错误 envelope。
- 拆分不得改变现有 API 路径和 `{ ok, msg, data }` envelope。

### P1-2：前端 `app.js` 暂不作为当前任务

现状：

- 前端主控制器已经覆盖登录、课表、公告、设置、网络、反馈、Course。
- 本轮只把 trusted account 的纯逻辑抽到模块，但主文件仍偏重。

当前裁决：

- 后端长期重构期间不主动拆前端。
- 后端只保证兼容层稳定，方便后续前端整体重构。

### P1-3：真实移动教务格式仍需持续验证

现状：

- fake 测试已覆盖主链路。
- 真实移动教务返回格式和 fake 样本存在差异的风险仍然存在。

建议：

- 继续使用真实链路验证工具交互输入账号密码。
- 原始响应只保留在临时数据根；仓库只接收脱敏 fixtures。
- 解析器采用宽容解析，缺字段进入 warning，不直接崩溃。

## 4. P2 问题

### P2-1：传统教务验证码只能放在 Course 边界

验证码 UI 未来只能出现在 Course 面板内的独立区域或弹层，不能回到主登录卡片。

当前保持：

- `traditional-jw-captcha-deferred`
- `/api/course/connect` 返回 deferred/unavailable。
- Cookie 课表刷新后置。

### P2-2：Telemetry/Feedback 云上传仍是 local-only

当前 local-only 是刻意边界，不是缺陷。

后续如果接云上传，需要单独切片处理：

- 传输加密。
- 重放队列。
- 云端失败重试。
- 配置密钥管理。

### P2-3：根仓库材料仍需隔离

当前活动入口应保持清晰：

- `XKE.DotNet8/`
- `web/`
- 当前 Python 运行代码区
- `docs/项目说明/`
- `重构计划/`

其余单次分析、旧脚本、构建规格和开发材料应进入 `reference-archive/`，只作参考，不参与默认开发决策。

## 5. 维护原则

- 先保证门禁，再扩功能。
- 只在已交付切片维护强类型契约。
- 不读写 Python legacy runtime 数据。
- 不提交真实账号、密码、token、`.env`、生产遥测或未脱敏响应。
- 注释只写在边界和副作用处：DPAPI、系统命令、local-only、blocked policy、deferred 能力。
