# WinUI 3 原生桌面 UI 预案

## 状态

- 本文只记录后续方向，不进入当前开发切片。
- 当前阶段仍保持 `WPF + WebView2 + WebHost + Web 前端` 的可用基线。
- 现有 Web 界面样式和交互应作为未来原生 UI 的视觉与行为参考。

## 方向判断

- 如果后续决定重构整个界面层，优先考虑 `WinUI 3 + C#` 原生桌面 UI，而不是继续扩展当前 Web SPA。
- 主要收益是桌面边界统一、强类型状态、MVVM 可维护性和原生窗口能力，不把性能作为唯一理由。
- `WebHost`、存储、认证、课表、公告、网络、反馈等后端边界仍按现有 .NET 主线推进，UI 技术切换不应反向污染核心业务层。

## 不在本轮推进

- 不立即替换当前 Web 前端。
- 不因为本预案引入新的前端框架或重写现有样式。
- 不在当前后端结构收敛阶段扩大 UI 迁移范围。

## 迁移原则

- 先冻结当前 Web UI 的视觉、交互和关键流程验收标准，再迁移。
- 使用 MVVM 分层，避免把新界面写成新的 `MainWindow` 巨石。
- 页面级逐步替换，优先从低风险页面开始：关于、更新、设置、网络状态，再进入登录和课表主界面。
- 原生 UI 通过稳定的应用服务或本地 API 契约访问业务能力，不直接读写运行时数据目录。
- 当前 WebView2 前端在迁移期间保留为回退界面和对照实现。

## 应用原生提醒边界

- 当前课程提醒的触发逻辑仍在 Web 前端：由已加载课表、提醒设置和实时节次计算提醒候选，再通过桌面桥接调用托盘通知。
- 当前 `Xke.DesktopHost` 已具备本地托盘气泡发送能力，但这只是发送通道，不是应用级提醒调度。
- 后续应将课程提醒迁移到应用原生能力：提醒设置读取、课表候选计算、定时触发、去重、发送记录和失败降级应收敛到 `DesktopHost/Core` 的 `Reminder/Notification` 边界。
- 迁移后的基本验收口径：软件关闭到托盘或开机静默启动后，不依赖 WebView 加载，也能基于本地课表按配置发送上课提醒。
- 第一阶段只做本地应用提醒，优先复用托盘/系统通知；邮件、微信、Webhook、云推送等外部通道不进入基础切片。
- 在原生提醒切片启动前，不继续扩大前端 `lessonReminder` 逻辑，避免把后台提醒能力绑定到 Web SPA 运行时。

## 启动条件

- 当前 `.NET` 后端主链路稳定，build/test/smoke 持续通过。
- `web/` 前端基线已纳入版本控制或以明确方式冻结。
- 已确认后续产品形态主要面向 Windows 桌面端，不要求同一套 UI 同时服务浏览器访问。
- 已确定 WinUI 3 打包、窗口、托盘、通知、单实例和 WebHost 生命周期的承载方案。
