# XKE.DotNet8 未来最终目标架构蓝图

## 1. 目标定位

XKE 的未来目标不是“把 Python 代码逐文件翻译成 C#”，而是演进成一套：

- **C# 内核**
- **C# Windows 宿主**
- **保留可复用 Web 前端壳**
- **正式化的控制平面（Notice / Access / Feature Flags / Fail-Closed）**

的稳定桌面产品。

---

## 2. 目标架构总览

### 2.1 DesktopHost
职责：
- 单实例
- 托盘
- 自启
- 静默启动
- 通知
- WebView2 宿主
- 生命周期管理

约束：
- 只做宿主层，不承载业务逻辑
- 不直接操作业务存储
- 不直接拼接业务 payload

---

### 2.2 WebHost
职责：
- 本地 HTTP API
- 中间件
- session/header 兼容
- 前端静态资源托管
- SPA fallback
- 业务路由入口

约束：
- 只做边界层与协议层
- 不成为新的业务巨石
- 路由层只负责编排，不直接承载复杂业务实现

---

### 2.3 Core
职责：
- `Auth`
- `NoticePolicy`
- `Schedule`
- `Course`
- `NetworkKeepAlive`
- `Feedback`
- `Telemetry`
- `DesktopSettings`

约束：
- Core 是业务真相源
- 控制平面必须是一等公民，而不是附属模块
- 各业务域边界应稳定收敛，防止演化出新的巨石类

---

### 2.4 Storage
职责：
- 新数据模型
- legacy 兼容读取
- 文件存储
- 本地状态持久化
- notice 本地缓存读取
- session / credentials / profile / preferences / settings 等持久层

约束：
- Storage 负责数据，不负责业务规则
- 兼容层是桥，不应永久成为主数据模型
- 最终应逐步完成从 legacy 表达向统一新表达的收口

---

### 2.5 Security
职责：
- secure-json
- DPAPI(CurrentUser)
- Ed25519 / notice signature
- hybrid secret
- 公钥解析
- 密钥路径与运行时安全资产解析

约束：
- Security 应保持“小而硬”
- 只做安全能力，不混入业务决策
- 所有安全规则应可被 Storage / Core / WebHost 复用

---

### 2.6 Contracts
职责：
- DTO
- API envelope
- 外部输入输出形状
- 共享枚举与字段名

约束：
- 只表达契约，不承载业务行为
- 契约优先服务“已落地切片”，不盲目提前冻结未来全部接口

---

## 3. 控制平面应有的正式地位

未来最重要的结构升级之一，是把 `Notice` 从“公告模块”提升为：

> **控制平面内核**

它至少应该统一承载：
- access decision
- feature flags
- feature limits
- readonly / blocked / fail-closed
- version policy
- update info
- status notice

它影响的域包括：
- `Auth`
- `Course`
- `WebHost` 中间件
- 前端行为与提示
- 未来宿主层的一部分运行策略

---

## 4. 前端未来定位

当前保留 `web/` 是合理的，因为它已经是可用资产。

未来定位应是：
- 展示层
- 交互层
- 状态消费层

而不应继续承担：
- 核心业务真相源
- 复杂控制平面决策
- 大量不可测试的 orchestrator 逻辑

也就是说：
- 现在保留前端是对的
- 未来不一定要重写成原生 C# UI
- 但业务必须逐步回收至 Core / WebHost / Storage / Security

---

## 5. 最理想的演进阶段

### 阶段 A：形成可运行产品内核
- DesktopHost 可启动
- WebHost 可运行
- Auth 可闭环
- NoticePolicy 可控制
- Schedule 可工作
- 数据兼容可验证

### 阶段 B：让兼容层逐步退场
- legacy preferences 退场
- legacy data 表达逐步退场
- 双轨 payload 输出逐步收口

### 阶段 C：产品化增强
- WebView2
- 托盘
- 自启
- 通知
- 单实例
- 宿主桥收口

### 阶段 D：视情况决定是否原生 UI 化
只有在 Web 壳确实成为维护负担时，才考虑把主界面重写为原生 C# 页面。

---

## 6. 必须避免的未来歪路

### 6.1 把兼容层永久化
兼容层必须有退出路径，否则会把系统越拖越重。

### 6.2 在 C# 中重建新的巨石
高风险对象包括：
- `AuthService`
- `NoticeCompatibility`
- `XkeWebHostApplication`

未来必须控制其膨胀。

### 6.3 过早追求极致抽象
当前阶段应优先“先能替代，再慢慢优雅”。

### 6.4 过早做 UI 大换血
宿主没稳、控制平面没稳时，重写 UI 会显著增加失败概率。

---

## 7. 最终理想状态

未来最好的 XKE 应该是：

### 技术上
- `.NET 8+`
- `WPF/DesktopHost`
- `ASP.NET Core/WebHost`
- 保留 Web 前端壳
- Storage / Security 独立
- Notice 控制平面稳定

### 结构上
- 宿主、边界层、业务层、数据层、安全层分工明确
- 旧兼容层逐步退场
- 各业务域可独立测试
- 控制平面能统一调度产品行为

### 产品上
- Windows 体验更稳
- 启动更可控
- 本地服务链路更清晰
- 维护成本更低
- 后续继续开发新能力时，不再受 Python 巨石结构拖累

---

## 8. 一句话总结

> XKE 的未来正确方向，是把它做成“**C# 内核 + C# 宿主 + 保留 Web 前端壳 + 正式化控制平面**”的稳定桌面产品，而不是简单把 Python 代码翻译成 C#。
