# XKE.DotNet8 传统教务人工登录开发计划

> 状态：future-only  
> 更新时间：2026-04-23  
> 当前不进入实现，仅保留后续切片边界。

## 1. 结论先行

传统教务验证码链路、OCR 识别、Cookie 课表和 Course 真实抢课，当前全部后置。

当前主线已经固定为：

- 移动教务承担首次初始化与课表维护。
- 主登录卡片只承担“新账号初始化 / 手动恢复”。
- 传统教务验证码未来只能出现在 `Course` 面板内的独立连接区域或弹层。

> 不允许把验证码输入框、验证码图片或 challenge 流程重新塞回主登录卡片。

## 2. 当前已知边界

当前 `.NET` 项目里的 Course 状态仍保持 deferred：

- `traditional-jw-captcha-deferred`
- `/api/course/connect` 当前生产实现不建立真实连接
- `/api/course/grab/start` / `/api/course/grab/stop` 当前固定 deferred

这不是遗漏，而是刻意冻结的边界。

## 3. 未来切片目标

未来若重新开启本计划，只做以下事情：

1. 传统教务 challenge 建模。
2. 验证码图片获取与刷新。
3. 人工输入验证码提交。
4. 传统教务登录上下文与 cookies/hidden fields 的运行时存储。
5. 连接成功后打通 Course `rounds / preview`。

以下继续后置：

- OCR 自动识别。
- 抢课真实轮询与限流。
- 传统教务连接与主登录流程融合。

## 4. UI 约束

未来验证码交互只允许采用以下形态之一：

- `Course` 面板内的独立连接区域。
- `Course` 面板触发的独立弹层。

明确禁止：

- 在主登录卡片增加验证码输入区。
- 在首次初始化表单里混入传统教务 challenge。
- 用验证码链路干扰当前移动教务 trusted/session 主线。

## 5. 技术约束

- 不引入 Python bridge。
- OCR 不作为当前前置条件。
- challenge、cookies、hidden fields 必须有独立运行时 store。
- Course 连接状态必须与移动教务 `connected` 分离。

## 6. 重新开启本计划前的前置条件

只有在以下条件满足后，才适合重开本计划：

- 当前移动教务 `Auth + Schedule` 真实链路已经稳定。
- 本地可信状态主线和 trusted account UX 已收敛。
- 真实验证码协议已经重新梳理完毕。
- Course 新框架已不再依赖旧 `/course/*` 兼容迁移。
